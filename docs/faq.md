# 常见问题

## 1. 明明已经填了 `AK/SK`，为什么还是鉴权失败

先检查这几项：

- `region` 是否真的是 `cn-north-4`
- 标准区域下是否误填了错误的 `*_base_url`
- 如果你走的是共享 `http + session` 模式，是否真的先调用了 `auth_configure_session`
- 如果你用的是固定 `auth_token` URL，token 是否已经过期，或是否被 `auth_clear_session` 撤销

## 2. 为什么 `Req` 能用，别的模块不行

这通常不代表整个 MCP 服务坏了，更常见的原因是：

- 某个具体产品地址不对
- 该产品在目标项目上没有开通
- 当前账号对该产品权限不足
- 当前租户没有足够业务数据
- 该路由在北京四未发布

建议按模块逐个验证，不要因为一个模块失败就把问题归到整套服务上。

## 3. 为什么共享部署还要每个人自己配 `auth_configure_session`

因为共享的是 MCP 服务，不是共享一套业务凭证。

这个项目的共享模型是：

- 服务端统一部署
- 每个用户的业务凭证隔离在自己的 session / auth record 中
- 服务端只保存加密后的凭证记录，不把一套固定 `AK/SK` 暴露给所有人共用

## 4. 共享模式下，客户端到底靠什么记住我

当前共享 `http` 模式支持三种恢复方式：

- session 还活着
- 客户端保留了 cookie
- 客户端使用固定 `auth_token` URL

所以“服务重启后还要不要重新配置”取决于：

- `MCP_AUTH_MASTER_KEY` 是否没变
- `MCP_AUTH_DATA_PATH` 是否还在
- 当前 token 是否还有效

## 5. 标准区域下，每个人都要配所有产品地址吗

一般不需要。

如果你是标准区域，通常只需要：

- 自己的 `AK`
- 自己的 `SK`
- 自己的 `region`

服务端会自动推导各产品的标准地址。

## 6. 为什么建议写操作优先先做受控验证

因为这样可以先确认：

- 参数是否合理
- 目标对象是否正确
- 当前租户/区域是否支持该路径
- 当前写链路是不是已经真正带上了用户身份

在 `Deploy` 这类写路径较多的模块里，这一点尤其重要。

## 7. 为什么调用有时会感觉慢

当前“慢”可能来自两种地方：

- 应用层首次冷请求
  - 会真实打上游 CodeArts API
- 外部链路
  - 客户端观测很慢，但服务进程日志里并没有对应慢请求

截至 `2026-04-20` 的最近联调，已经确认：

- 共享 `http` 模式下，部分缓存命中请求在服务日志里已经是毫秒级
- 外部偶发高延迟和 `502` 仍可能来自入口网络层

所以判断“是不是项目本身慢”，最好同时看：

- 客户端侧耗时
- 服务端 `durationMs`
- `upstreamDurationMs`
- `cacheHits`

## 8. 为什么有些模块还是 `Partial`

最常见的原因有三个：

- 代码已经实现，但当前租户没有对应业务数据
- 官方接口在北京四没有发布
- 写路径已实现，但还缺稳定正样本或健康模板样本

也就是说，`Partial` 往往不是“没 MCP 化”，而是“真实环境还有客观限制”。

## 9. 为什么会看到 `502`

先不要默认认定是 MCP 应用本身崩了。

最近联调已经遇到过一种情况：

- 客户端请求返回 `502`
- 但 `codearts-mcp.service` 日志里并没有对应请求

这说明问题可能发生在：

- 外部入口网络层
- 反向代理层
- 客户端到服务器之间的链路

而不是应用 handler 自己返回了 `502`。

## 11. 共享 HTTP 持久化鉴权到底带来了什么

用户第一次调用 `auth_configure_session` 后，服务器会把该用户的 CodeArts 凭证加密保存，并签发稳定的 auth cookie/token。

这意味着：

- 客户端保留 cookie 时，后续正常重连不需要再次填写 `AK/SK`
- 客户端不保留 cookie 时，也可以把返回的 `auth_token` 固定写到 MCP URL 里继续复用
- 只要服务器端的 `MCP_AUTH_MASTER_KEY` 和 `MCP_AUTH_DATA_PATH` 保持不变，服务重启后也能恢复
- 如果想撤销当前用户已保存的凭证，调用 `auth_clear_session`

## 12. 为什么不建议直接把 `AK/SK` 写进共享客户端配置

本项目推荐不要把 `AK/SK` 直接写进共享 HTTP 客户端配置，原因有两个：

- 客户端配置文件更容易被复制、同步或误提交
- 共享 HTTP 模式已经提供了更合适的入口：`auth_configure_session`

推荐方式是：

1. 客户端配置里只写共享服务地址
2. 连上后调用 `auth_configure_session`
3. 让服务端加密持久化保存当前用户凭证
